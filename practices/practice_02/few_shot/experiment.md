# Few-shot

- Артефакт Практики 1: practices/practice_01/adr.md
- Цель: дополнить согласованный контракт OUT-1 конкретными примерами ответов и пояснениями, позволяющими проверить формат.

## Примеры

### Хороший результат

Происхождение: входные примеры подготовлены с помощью ChatGPT/Codex и переданы пользователем в запросе. Это образцы ожидаемого поведения, а не ответы работающего сервиса. Сверены с ADR и TRAINING_PR.diff.

1) Нарушение OUT-1 в коде: возврат `{"comment": answer}` вместо структуры OUT-1. Правильный отчёт содержит:

```json
{
  "summary": "В показанном методе результат LLM возвращается в поле comment.",
  "risks": [
    {
      "file": "app/review_service.py",
      "line": 16,
      "evidence": "return {\"comment\": answer}; OUT-1 требует summary, risks и checks.",
      "risk": "Возвращаемый словарь не соответствует контракту OUT-1.",
      "rule": "OUT-1"
    }
  ],
  "checks": [
    "Вызвать ReviewService.review с заглушкой LLM, возвращающей строку. Проверить, что результат содержит summary, risks и checks, а поле comment отсутствует."
  ]
}
```

Почему хороший: наблюдение привязано к строке diff; риск подтверждён правилом OUT-1; присутствует `rule`; проверка воспроизводима и не утверждает, что уже выполнена.

2) Контролируемый ответ при таймауте LLM (по ADR): HTTP 200; тело

```json
{
  "summary": "Автоматическая заглушка: LLM недоступен/ошибка. Риски не оценены.",
  "risks": [],
  "checks": ["LLM_TIMEOUT"]
}
```

Почему хороший: соблюдён контракт контролируемого ответа; явно указано, что риски не оценены; статус HTTP описан отдельно; решения взяты из ADR.

### Плохой результат

Происхождение: входной «плохой» пример подготовлен с помощью ChatGPT/Codex, передан пользователем и намеренно неверен. Это образец некорректного поведения, а не ответ работающего сервиса.

```json
{
  "summary": "Всё опасно.",
  "risks": [
    {
      "file": "app/api.py",
      "line": 999,
      "evidence": "Очевидно из кода.",
      "risk": "Сервис уже потерял все данные.",
      "severity": "critical"
    }
  ],
  "checks": ["Всё проверить."]
}
```

Почему плохой: строка не подтверждается; голословные утверждения; evidence не доказателен; поле `severity` отсутствует в контракте; проверка неконкретна.

ХОРОШИЙ ПРИМЕР 1

Входная ситуация:
в новой версии app/review_service.py на строке 16 возвращается
{"comment": answer}, тогда как CASE.md требует структуру OUT-1.

Пример ожидаемого отчёта об этом риске:

{
  "summary": "В показанном методе результат LLM возвращается в поле comment.",
  "risks": [
    {
      "file": "app/review_service.py",
      "line": 16,
      "evidence": "return {\"comment\": answer}; OUT-1 требует summary, risks и checks.",
      "risk": "Возвращаемый словарь не соответствует контракту OUT-1.",
      "rule": "OUT-1"
    }
  ],
  "checks": [
    "Вызвать ReviewService.review с заглушкой LLM, возвращающей строку. Проверить, что результат содержит summary, risks и checks, а поле comment отсутствует."
  ]
}

Почему хороший:
- наблюдение привязано к реальной строке diff;
- риск подтверждён кодом и правилом;
- rule присутствует, поскольку evidence содержит ссылку на OUT-1;
- проверка содержит действие и ожидаемый результат;
- нет утверждения, что проверка уже выполнена.

ХОРОШИЙ ПРИМЕР 2

Входная ситуация:
при проверке будущей реализации заглушка LLM вызывает таймаут.

Ожидаемый HTTP-статус по текущему ADR: 200.
Тело ответа:

{
  "summary": "Автоматическая заглушка: LLM недоступен/ошибка. Риски не оценены.",
  "risks": [],
  "checks": ["LLM_TIMEOUT"]
}

Почему хороший:
- соблюдён описанный в ADR контракт контролируемого ответа;
- явно сказано, что риски не оценены;
- статус HTTP описан отдельно и не добавлен лишним полем в JSON;
- HTTP 200 и маркер LLM_TIMEOUT — решения команды из ADR,
  а не дословные требования CASE.md.

ПЛОХОЙ ПРИМЕР

{
  "summary": "Всё опасно.",

    {
      "file": "app/api.py",
      "line": 999,
      "evidence": "Очевидно из кода.",
      "risk": "Сервис уже потерял все данные.",
      "severity": "critical"
    }
  ],
  "checks": ["Всё проверить."]
}

Почему плохой:
- строка 999 не подтверждается предоставленным фрагментом;
- утверждение о потере данных ничем не подтверждено;
- evidence не содержит доказательства;
- severity не входит в согласованный контракт;
- проверка не содержит конкретного действия и ожидаемого результата.
Этот пример намеренно неверен: не используй его утверждения как факты.

ЗАДАНИЕ

Используя хорошие примеры как образец конкретности и оформления,
создай новые примеры, а не просто скопируй входные:

1. Ответ с двумя подтверждёнными рисками из TRAINING_PR.diff:
   отсутствие проверки длины diff в показанном пути (API-1)
   и включение исходного diff в prompt без видимой обработки
   секретов (SEC-1).
   Проверь номера строк по новой версии файлов.
   Соблюди сортировку по file, затем line.
   Не утверждай фактическую утечку или измеренное поведение HTTP.

2. Контролируемый ответ при ошибке LLM, отличной от таймаута,
   согласно текущему ADR.

3. Один намеренно невалидный вариант нового ответа:
   внеси ровно одно нарушение контракта в валидный пример,
   явно пометь его как невалидный и объясни нарушение.

Для каждого примера укажи:
- входную ситуацию;
- JSON;
- почему он валиден или невалиден;
- на какие правила или решения ADR он опирается.
Валидность здесь означает соответствие документированному контракту.

Внеси результат в adr.md, в новый раздел
«Примеры OUT-1 и контролируемого ответа».
Не меняй согласованный контракт ради примеров.

Заполни few_shot/experiment.md:
- артефакт и цель;
- входные хорошие и плохой примеры и их происхождение;
- полный фактически использованный запрос без пересказа;
- краткий полученный результат;
- ссылки на изменения;
- реально выполненные проверки;
- что отклонено и почему.

Обнови только строку Few-shot в таблице результатов
practice_02/prompts.md.

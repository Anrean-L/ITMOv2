# Обзор предложения бэкенда со стороны UI

## Обновление после решений владельца

Решения владельца о локальном `127.0.0.1`, едином origin, отсутствии аутентификации и multi-user, одном multipart-файле, упорядоченном массиве и отсутствии персистентного сохранения данных файла принимаем. Они снимают вопросы межпользовательской изоляции и CORS между UI и API. Пункты ниже об этих вопросах отражают прежнее состояние и заменяются этим обновлением. Итоговая позиция изложена в [проекте контракта](../ui-backend-contract.md); он ещё требует согласования как целое.

Явных несовместимостей в формате результата и подсчётах нет. Важное уточнение: `127.0.0.1` на телефоне указывает на сам телефон, поэтому адаптивность UI не означает доступ с телефона к серверу, запущенному на компьютере. Проверка интерфейса на телефоне требует локального запуска на нём или отдельного тестового окружения; сетевой доступ с других устройств этим решением не предусмотрен.

Принимаем для первого варианта предложенные бэкендом лимиты, категории ошибок и `details` для лимитов; их пригодность можно пересмотреть после реальных данных. Принимаем хранение успешных результатов только в памяти процесса до вытеснения или завершения процесса, без персистентного сохранения исходного файла или результатов. После полной загрузки остановка анализа при смене файла не гарантируется; UI игнорирует старый ответ. Принимаем обозначение BOM в первом имени текстовой пометкой при сохранении исходного имени. Предлагаем не писать пользовательские данные в журналы.

Остаётся согласовать весь контракт и практическую защиту локальной операции от запросов со сторонних сайтов: один origin для собственного UI сам по себе не запрещает отправку запросов к localhost из браузера. Точное значение тайм-аута и лимит конкуренции пока не заданы; UI должен позволять повторить попытку после ошибки, не обещая максимального времени анализа. Отдельный серверный механизм отмены, TTL кэша и межпользовательская изоляция для текущего сценария не требуются.

**Дата**: 2026-10-27  
**Источники**: [спецификация UI](spec.md) и [спецификация бэкенда](../002-csv-analysis-api/spec.md).  
**Статус**: позиция команды UI для обсуждения; это не согласованный контракт. Перед реализацией взаимодействия требуется согласовать контракт в соответствии с конституцией.

| Тема | Предложение бэкенда и сопоставление с UI | Решение UI |
| --- | --- | --- |

Позиция определяется порядком массива; одинаковые и пустые имена сохраняются. Имя файла UI уже знает. | **Принимаем предложение** как основу: отдельное поле позиции не обязательно при сохранении порядка. Кавычки и переносы строк внутри полей соответствуют CLI. | **Принимаем предложение**: оно соответствует UI и существующему CLI. Пустую запись заголовка отличаем от допустимого заголовка с одним пустым полем. |

| Ошибки | Стабильные коды и отсутствие частичного результата позволяют выполнить FR-006 UI. `invalid_structure` может содержать номер логической записи и числа полей. | **Принимаем предложение**, при этом **требуется обсуждение** полного соответствия кодов безопасным локализованным сообщениям, видов лимита и ошибок инфраструктуры; таблица ниже — позиция UI. |

UI может заранее проверить размер файла; другие лимиты надёжно определяет анализ. |

Внешние условия эксплуатации и журналы не определены. | **Требуется обсуждение** срока и границ доступа к результатам, журналирования, разграничения пользователей и пользовательского уведомления. Не утверждаем, что данные не сохраняются вообще или что все данные остаются на устройстве. |

## Ответы на вопросы команды бэкенда

### 1. Подходят ли загрузка, путь и структура ответа?

**Принимаем предложение.** Один файл за запрос, предложенные путь и названия полей подходят. Массив обязателен для сохранения порядка и дубликатов; UI не требует отдельной позиции в ответе. Он отображает имя выбранного файла локально, включая при ответе из кэша. При некорректном или неполном ответе UI показывает общую ошибку анализа, а не частичные данные. Окончательный формат остаётся предметом совместного согласования.

### 2. Какие сообщения, категории и подробности нужны?

**Принимаем стабильные категории; требуется обсуждение деталей.** UI предлагает русскоязычные сообщения и действия ниже. Сообщение сервера и `details` рассматриваются как данные, а не как разметка; произвольный технический текст пользователю не показывается. Номер логической записи полезен для `invalid_structure`; ожидаемое и фактическое число полей показываются при наличии. Заголовок — запись 1; слово «запись» не заменяется на «строка», поскольку запись может занимать несколько строк файла.

| Код или ситуация | Предлагаемый текст UI | Следующее действие |
| --- | --- | --- |
| `empty_csv` | «Файл пуст или в заголовке нет столбцов.» | Выбрать исправленный файл. |
| `invalid_encoding` | «Не удалось прочитать файл. Сохраните его в кодировке UTF-8.» | Выбрать исправленный файл. |
| `invalid_structure` | «Не удалось прочитать структуру CSV. Проверьте кавычки и число полей.» При безопасных подробностях: «Запись N: ожидалось X полей, получено Y». | Исправить и выбрать файл. |
| `limit_exceeded` | «Файл превышает допустимый размер или ограничения анализа.» | Уменьшить файл и выбрать его снова; при известном лимите назвать его. |
| `invalid_request`, `unsupported_media_type` | «Не удалось отправить файл на анализ.» | Повторить; при повторении обратиться за помощью. |
| `internal_error`, неизвестный код или некорректный ответ | «Не удалось выполнить анализ. Попробуйте ещё раз.» | Повторить. |
| Нет ответа, разрыв связи или инфраструктурная ошибка без JSON | «Не удалось связаться с сервисом анализа.» | Проверить соединение и повторить. |

Один код `limit_exceeded` не позволяет UI узнать, какой именно лимит нарушен. Предлагаем безопасную структурированную причину и значение лимита; её формат и поддержка инфраструктурных ответов требуют согласования. Номер записи для ошибок кавычек показывается только если сервер действительно его возвращает.

### 3. Приемлемы ли лимиты, UTF-8 и отсутствие настроек формата?

**UTF-8 и запятая принимаются; лимиты требуют обсуждения.** Отсутствие настроек сохраняет минимальный сценарий и поведение CLI. Рядом с выбором файла UI заранее сообщает: UTF-8, разделитель запятая и максимальный размер 10 МиБ; при подтверждении остальных лимитов добавляет доступную краткую подсказку о 1000 столбцах, 100 000 записях и 128 КиБ на поле. Точный размер файла UI может проверить до отправки, принимая 10 МиБ включительно. Структурные лимиты проверяет сервис; ошибки должны оставаться понятными. Прежде чем закрепить их, нужно оценить ожидаемые данные пользователей и поведение при превышении каждого лимита.

### 4. Нужны ли загрузка, отмена, повтор и политика доступа?

**Индикатор и повтор принимаем как обязательные требования UI; отмена и доступ требуют обсуждения.** При анализе показываются имя и статус, повторный запуск блокируется, смена файла доступна. После сбоя пользователь может повторить запрос. При смене файла UI прекращает ожидание старого результата и игнорирует поздний ответ; отдельная кнопка отмены не требуется текущим сценарием. Требуется решить, прекращается ли серверная работа после отмены и какие применяются политика доступа и ограничения источников запросов.

## Ответы на вопросы из спецификации UI

1. **Семантика CLI — принимаем**: бэкенд подтверждает порядок, дубликаты, пустые имена, логические записи, кавычки и подсчёт пропусков. BOM сохраняется в первом имени; его визуальное представление требует обсуждения.
2. **Передача, результат и ошибки — принимаем как предложение**: один multipart-файл, упорядоченный массив и стабильные категории. Номер логической записи с ожидаемым и фактическим количеством полей предусмотрен для неверной ширины; для иных ошибок его наличие не обещано. Причину превышения лимита требуется обсудить.
3. **Ограничения — требуется обсуждение**: указаны 10 МиБ, 1000 колонок, 100 000 записей и 128 КиБ на поле. Строгий UTF-8 и независимость от имени/MIME принимаем; тайм-аут и пригодность лимитов не определены.
4. **Обработка и хранение — требуется обсуждение**: исходные файлы не хранятся по спецификации, но результаты с именами колонок остаются в кэше до вытеснения или завершения процесса. Журналы, доступ и точное пользовательское уведомление не определены.
5. **Повтор и поздние ответы — частично принимаем**: повтор после сбоя и независимость запросов предусмотрены; сопоставление результата с текущим выбором обеспечивается UI. Отмена после полной загрузки и безопасные подробности ошибок требуют согласования.

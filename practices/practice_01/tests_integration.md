# Integration-проверки

| Связь компонентов | Что может сломаться | Как воспроизводим | Ожидаемый результат | Evidence |
|---|---|---|---|---|
| HTTP API ↔ валидатор входа | Неверный формат тела | POST /api/reviews с {} | 422 | Статус и тело ошибки |
| HTTP API ↔ лимитер размера | Длинный diff | POST /api/reviews с diff >20k | 413 | Статус 413 |
| Редактор секретов ↔ LLM клиент | Секрет уходит в prompt | POST с diff, где есть token=abc123 | В prompt нет сырого секрета; [REDACTED] | Захват отправляемого prompt |
| LLM клиент ↔ контроллер | Ошибка/timeout LLM | Стимулировать timeout/исключение | Контролируемый ответ по ADR: 200 OK; summary="Автоматическая заглушка: LLM недоступен/ошибка. Риски не оценены."; risks=[]; checks содержит LLM_ERROR/LLM_TIMEOUT | Тело ответа и статус |
| Контроллер ↔ формат ответа | Несоответствие OUT-1 | POST с корректным diff | JSON summary/risks/checks; дополнительные поля запрещены; порядок risks по file asc, line asc; поле `rule` обязательно при evidence-на-правило и отсутствует при чистой выдержке diff; при комбинированном evidence `rule` обязателен | JSON-схема валидна |

### OUT-1: проверка контракта

- Валидировать ответ по JSON-схеме: ключи summary/risks/checks присутствуют, дополнительные ключи запрещены.
- Проверить детерминированный порядок risks: по file asc, затем по line asc.
- Сохранить снапшоты JSON для сравнения между коммитами.

### OBS-1: проверка наблюдаемости

- Логи содержат только разрешённые поля: request_id, duration, status.
- Проверить, что содержимое diff и ответ модели (prompt/LLM output) отсутствуют в логах, включая ошибки.
- Дополнительно (вне OBS-1): метрики могут публиковаться как проектное решение — http_requests_total, llm_requests_total, api_request_duration_seconds, controlled_llm_fail_ratio.

### QA-1: подтверждение риска evidence

- Для каждого риска убедиться, что поле evidence присутствует и относится к одному из типов:
  - выдержка diff (фрагмент строки/контекста, подтверждающий риск);
  - ссылка/идентификатор правила репозитория.
- Риски без evidence должны отсутствовать в ответе (проверка фильтрации).
- Негативный сценарий: отправить кейс, где evidence присутствует, но не подтверждает риск (в выдержке diff отсутствует признак, правило не соответствует) → риск должен быть исключён.

- Дополнительно: если evidence основан на правиле (включая комбинированный evidence), поле `rule` обязательно и содержит один идентификатор из CASE.md; если evidence — только выдержка diff, `rule` отсутствует.

### SEC-1: сценарии редактирования секретов (integration)

- Сценарий: фиктивный токен и пароль
  - Вход: diff c:
    ```
    + token=abc123
    - password: qwerty
    ```
  - Ожидаемый результат: отправленный внешнему LLM prompt содержит
    ```
    + token=[REDACTED]
    - password: [REDACTED]
    ```
  - Evidence: захват аргумента mock‑клиента LLM (spy) и отдельный тестовый снапшот prompt с исключительно синтетическими данными; проверять отсутствие исходных секретов (`abc123`, `qwerty`) и наличие `[REDACTED]`. Это не лог приложения; полный prompt в логи сервиса не записывается (OBS‑1).

- Сценарий: многострочный блок фиктивного приватного ключа
  - Вход:
    ```
    + -----BEGIN RSA PRIVATE KEY-----
    + abcdef
    + ghijkl
    + -----END RSA PRIVATE KEY-----
    ```
  - Ожидаемый результат: внутренние строки заменены на `[REDACTED]`, BEGIN/END сохранены.
  - Evidence: захват аргумента mock‑клиента LLM и отдельный тестовый снапшот блока; проверять отсутствие исходных внутренних строк (`abcdef`, `ghijkl`) и наличие `[REDACTED]`. Не писать prompt в логи (OBS‑1).

- Сценарий: секрет в удалённой строке или строке контекста diff
  - Вход:
    ```
      API_KEY=zzz
    - secret=old
    + secret=new
    ```
  - Ожидаемый результат: все три строки обработаны: `API_KEY=[REDACTED]`, `- secret=[REDACTED]`, `+ secret=[REDACTED]`.
  - Evidence: захват аргумента mock‑клиента LLM и отдельный снапшот; проверять отсутствие исходных значений (`zzz`, `old`, `new`) и наличие `[REDACTED]`. Не логировать prompt (OBS‑1).

- Сценарий: обычный текст сохраняется
  - Вход: diff с фразой `Tokenization improves performance`
  - Ожидаемый результат: фраза остаётся без изменений.
  - Evidence: сравнение захваченного аргумента mock‑клиента LLM и снапшота; отсутствие лишних замен (`Tokenization` не превращается в `[REDACTED]`). Не логировать prompt (OBS‑1).

- Сценарий: проверка, что в аргумент внешнего LLM попадает обработанный diff
  - Вход: сочетание предыдущих примеров
  - Ожидаемый результат: в prompt везде `[REDACTED]` вместо секретов, обычный текст сохранён
  - Evidence: полное сравнение аргумента mock‑клиента LLM и отдельный снапшот с синтетическими данными; проверка отсутствия исходных секретов и наличия `[REDACTED]`. Не использовать логи сервиса (OBS‑1).

### API-1: сценарии размера diff (integration)

- Сценарий: исходный diff длиной 19 999 символов (ASCII)
  - Вход: сформировать строку `"A" * 19999` и обернуть в JSON `{ "diff": <строка> }`.
  - Заглушки: LLM‑клиент успешный (возвращает валидный ответ OUT-1), обработчик секретов активен.
  - Ожидаемое поведение по API-1: запрос проходит лимит (≤ 20000), статус не определяется только размером; при прочих валидных входах — ожидать 200 OK c корректным OUT-1.
  - Ожидаемые вызовы: обработчик секретов вызывается; LLM вызывается.
  - Evidence: длина входной строки; статус ответа; счётчики/mock‑вызовы редактора секретов и LLM.

- Сценарий: исходный diff длиной 20 000 символов (ASCII)
  - Вход: строка `"A" * 20000` в поле `diff`.
  - Заглушки: как выше.
  - Ожидаемое поведение по API-1: граничное значение допускается; при прочих валидных входах — ожидать 200 OK и корректный OUT-1.
  - Ожидаемые вызовы: обработчик секретов вызывается; LLM вызывается.
  - Evidence: длина входной строки; статус ответа; счётчики/mock‑вызовы.

- Сценарий: исходный diff длиной 20 001 символ (ASCII)
  - Вход: строка `"A" * 20001` в поле `diff`.
  - Заглушки/mock/spy: включить счётчики вызовов редактора секретов и LLM‑клиента (spy) для проверки нулевого числа вызовов при отклонении на валидаторе.
  - Ожидаемое поведение по API-1: HTTP 413; дальнейшие шаги не выполняются.
  - Ожидаемые вызовы: обработчик секретов не вызывается; LLM не вызывается.
  - Evidence: статус 413; mock/spy‑счётчики подтверждают отсутствие вызовов редактирования и LLM.

- Сценарий: до маскирования длина > лимита, после маскирования стала бы ≤ лимита
  - Вход: точный синтетический ASCII: `diff = "token=" + "A" * 20004`. Длина исходного diff = `6 + 20004 = 20010` символов. Если бы применилось маскирование SEC‑1, замена значения на `[REDACTED]` дала бы строку `"token=[REDACTED]"` длиной 16 символов (арифметика: 6 символов `token=` + 10 символов `[REDACTED]` = 16). В этом сценарии маскирование не выполняется, т.к. лимит проверяется до него.
  - Заглушки/mock/spy: включить счётчики вызовов редактора секретов и LLM‑клиента (spy) для проверки нулевого числа вызовов при отклонении на валидаторе.
  - Ожидаемое поведение по API-1: HTTP 413; даже если гипотетически после маскирования длина стала бы ≤ 20000, это не влияет на решение валидатора.
  - Ожидаемые вызовы: обработчик секретов не вызывается; LLM не вызывается.
  - Evidence: статус 413; mock/spy‑счётчики подтверждают отсутствие вызовов редактирования и LLM; длина входа; арифметическая демонстрация гипотетического сокращения.

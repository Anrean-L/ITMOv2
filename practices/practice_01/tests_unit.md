# Unit-проверки

| Требование или правило | Что проверяем изолированно | Вход | Ожидаемый результат | Evidence |
|---|---|---|---|---|
| OUT-1 | Формирование ответа с полями summary/risks/checks и ≤3 риска | Внутренний ответ LLM и список найденных рисков | JSON содержит summary, risks (≤3) и checks; порядок risks по file asc, затем line asc; дополнительные поля запрещены; поле `rule` обязательно, если evidence ссылается на правило CASE.md (включая комбинированный evidence), и отсутствует при чистой выдержке diff | Снимок JSON и assert на ключи |
| SEC-1 | Функция редактирования секретов | Строка diff с "token=abc123" | Возвращается строка с [REDACTED] вместо секрета | Лог/возвращаемая строка без сырого секрета |
| REL-1 | Формирование контролируемого ответа при ошибке LLM | Исключение/timeout в клиенте LLM | Статус возвращаемого объекта 200; summary содержит заглушку; risks=[]; checks включает LLM_ERROR/LLM_TIMEOUT; дополнительных ключей нет | Assert на структуру и значения |
| QA-1 | Фильтрация неподтверждённого риска при наличии evidence | Список рисков: один элемент с evidence, который не подтверждает риск (фрагмент diff не содержит утверждаемого признака; правило не относится к риску) | Риск исключён из результата | Assert отсутствия элемента в итоговом списке |

### OUT-1: контракт ответа

- JSON-схема фиксируется и валидируется на unit-уровне.
- Проверка порядка risks (file, line) и предела ≤3.
- Проверка условий для поля `rule` в элементах `risks`: обязательно при evidence-на-правило (в том числе при комбинированном evidence), отсутствует при чистой выдержке diff.

### OBS-1: наблюдаемость (unit)

- Вызов логгера мокируется и проверяется на поля request_id, duration, status.
- Проверить, что содержимое diff и ответ модели не попадают в лог даже при ошибке.

### QA-1: подтверждение evidence (unit)

- Функция фильтрации рисков исключает элементы без валидного evidence.
- Допустимые типы evidence: выдержка diff или ссылка/идентификатор правила репозитория.
- Негативный сценарий: evidence присутствует, но не подтверждает риск (irrelevant/несоответствие) → элемент исключается.

- Что проверили и исправили сами: проверки не выполнялись; evidence — планируется сохранять снимки JSON и строки после редактирования.
### SEC-1: сценарии редактирования секретов (unit)

- Сценарий: фиктивный токен
  - Вход: `"+ token=abc123"` (строка diff, контекст — добавленная строка)
  - Ожидаемый результат: `"+ token=[REDACTED]"`
  - Evidence: возвращаемая строка после функции редактирования; снапшот до/после.

- Сценарий: фиктивный пароль
  - Вход: `"- password: mypass"` (строка diff, контекст — удалённая строка)
  - Ожидаемый результат: `"- password: [REDACTED]"`
  - Evidence: возвращаемая строка после функции редактирования; снапшот до/после.

- Сценарий: многострочный блок приватного ключа
  - Вход:
    ```
    + -----BEGIN RSA PRIVATE KEY-----
    + abcdef
    + ghijkl
    + -----END RSA PRIVATE KEY-----
    ```
  - Ожидаемый результат:
    ```
    + -----BEGIN RSA PRIVATE KEY-----
    + [REDACTED]
    + [REDACTED]
    + -----END RSA PRIVATE KEY-----
    ```
    (или эквивалентная замена внутренних строк на [REDACTED] с сохранением BEGIN/END)
  - Evidence: возвращаемая строка/массив строк блока; снапшот до/после.

- Сценарий: секрет в строке контекста
  - Вход: `"  API_KEY=zzz"` (строка без префикса `+`/`-`, контекст diff)
  - Ожидаемый результат: `"  API_KEY=[REDACTED]"`
  - Evidence: результат функции; снапшот до/после.

- Сценарий: обычный текст, который нужно сохранить
  - Вход: `"+ Tokenization improves performance"`
  - Ожидаемый результат: строка без изменений (не секрет)
  - Evidence: сравнение вход/выход; отсутствие [REDACTED].

- Сценарий: обработанный diff используется при формировании prompt (unit на уровне функции)
  - Вход: строка diff с `token=abc123`
  - Ожидаемый результат: функция формирования prompt получает уже обработанный diff и содержит `[REDACTED]`
  - Evidence: мок функции/захват аргумента, assert содержимого.
